# Manager Insights — Master End State, Transition & Implementation Plan

**Purpose:** Single **execution document** that merges [manager_insights_vo.md](manager_insights_vo.md) (product vocabulary + report shape), [manager_insights_coordination_plan.md](manager_insights_coordination_plan.md) (target architecture), and [manager_insights_vo_to_coordination_transition.md](manager_insights_vo_to_coordination_transition.md) (migration + admin matrix). It also aligns with [manager_insights_implementation_plan.md](manager_insights_implementation_plan.md) for **what is already shipped** in code.

**How to use this file**

- Work **top to bottom** on **§6** — **Steps 1–46** (checklist only; see **§1** numbering note) — one PR-sized deliverable each; order encodes dependencies.
- After each step: set **Done** to `yes` (or check the box), note **PR / commit** in your tracker; optional **Notes** column in your copy of the table.
- **DB** rows require Alembic migration + rollback notes before merge.
- **Admin-complete** = you can verify that step on **Admin → Manager insight** (or the listed admin API) without Slack, where **Admin** is non‑`—`.
- **Step-complete** = **Done** is checked only after **§6.2 Verification** for that **§6 step** is satisfied (automated tests green + any listed manual check signed off).

### Recommended order: cleanup vs build

**Do not start by deleting large chunks of the old pipeline.** The admin surface today depends on **interpretations + insights** for a full trace; removing them first leaves you without a working QA story.


| Phase                  | What you do                                                                                                                                                                                               | Why                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **A — Add (default)**  | Follow **§6 from Step 1 onward**: each micro-step adds or exposes one thing; feature flags default **off** until ready.                                                                                   | **Parallel runway:** old behavior stays until the new slice is visible in admin/API. |
| **B — Demote**         | **Steps 35–36** (skip narrative query + admin toggles) so coordination runs are fast; hide legacy panels when stable.                                                                                     | **Product switch** without a risky “big delete”.                                     |
| **C — Remove / clean** | Delete or slim code **only after** decisions (and optionally apply/outcomes) are real: dead imports, unused `ReportV0` builders if never wired, duplicate helpers, tests that only covered removed paths. | Avoids breaking bisect / admin parity mid-migration.                                 |


So: **first build the new path + admin visibility in narrow steps**; **then** turn off what you no longer need; **last** remove dead code in small PRs.

## Locked architecture decisions (before §6 Step 1)


| Topic                      | Lock                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Perception vs evidence** | `**PerceptionRow`** = separate Pydantic model (LLM-shaped: state, ambiguity, deps, etc.). `**EvidenceItem`** = minimal regex-backed contract; **do not** add perception fields to it. From `**link_work_items`** through `**compute_signals`**, code reads **only** a **normalized, validated bundle** built from validated `PerceptionRow` + `EvidenceItem` rules — **never** raw LLM JSON. |
| **Pipeline order**         | **2 → validated perception (3) → links (4).** `**link_work_items` runs only after** perception validation.                                                                                                                                                                                                                                                                                   |
| **ExecutionGraph**         | **Ephemeral only** — in-memory for the run; **no** DB table, **no** persistence, **no** partial storage.                                                                                                                                                                                                                                                                                     |
| **Decision engine (V1)**   | `**GapBundle` required** — every `DecisionItem` **must** reference a gap; no gap-only-by-signal in V1. **Signals** = prioritization / tie-break. **Graph** = supporting context in templates/rules only.                                                                                                                                                                                     |
| **Step 7.5**               | **Single sorted list**, `**max_decisions_surfaced` = 3** default — **no** clustering, **no** batching.                                                                                                                                                                                                                                                                                       |


**Flexible at implementation time (record in each PR):** settings **env vs DB** (**Step 6**); SQL **table/column names** (**Step 30+**); **Slack signing** details (**Step 44+**).

**Rule:** If it touches **data model, pipeline order, or inter-step contracts**, it is governed by the table above — **not** re-decided in standup.

## 2. End state (what “done” looks like)

### 2.1 Product (from coordination + VO alignment)

- **Primary user value:** A **system that keeps execution moving** — **decisions** (verifiable next steps) over long passive reports; [coordination plan intro](manager_insights_coordination_plan.md).
- **Default Slack surface:** **Decision blocks** (title, type, rationale, suggested action, evidence links, decision id, run id) with **Approve / Modify / Ignore**; receipts in-thread; optional outcome pings writing `**OutcomeItem`** — not model output [coordination §5](manager_insights_coordination_plan.md#5-slack--api-delivery).
- **VO language rules** preserved in all user-facing strings: e.g. “not found in available tracked systems”, no blame tone [VO Report Mapping / language rule](manager_insights_vo.md).
- **Narrative report** (`Interpretations` / `Insights` / `ReportV0`-style): **optional**, behind flags; **must not** block decision generation [transition §4](manager_insights_vo_to_coordination_transition.md#4-what-to-remove-or-demote-product--code-paths).

### 2.2 Technical (from coordination plan)


| Layer                                  | Behavior                                                                                                                                                                                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Perceive (Step 3 + validation)**     | LLM-assisted **execution state perception**: kinds + state/transitions + `waits_on` / `blocked_by` + commitment strength + `risk` + `ambiguity` (`unclear_scope`                                                                             |
| **Structure (2, 3 validated, 4, 4.5)** | `WorkItemBundle`, validated perception, `LinkBundle`, ephemeral `**ExecutionGraph`** (`ExecutionNode`, `ExecutionEdge`). **Graph not persisted**; source of truth = work items, evidence/perception rows, decisions, outcomes.               |
| **Detect (5, 5.5, 5.6, 6)**            | Same four **base gap types** as today + optional graph-assisted predicates; extended **signals** (`scope_ambiguity`, `discussion_churn`, `contradiction_density`, etc.) with `level` + `explain`. **No LLM.**                                |
| **Decide (7, 7.5)**                    | **Rule-only**; **V1:** every `DecisionItem` **requires** a `GapItem` (see **Locked**). Signals adjust **order** only; **flat** sort + cap **3**; **no** clustering. Optional `**decision_debug`** / `**decision_emission_debug`** for admin. |
| **Act (coordination Step 8)**          | Connector writes + idempotency; **no LLM.**                                                                                                                                                                                                  |
| **Learn (10.6)**                       | `**OutcomeItem`** + deterministic evaluation + **policy tables** (not ML training).                                                                                                                                                          |


### 2.3 Gap → decision (base + extensions)

**Base (unchanged predicates from VO / current code):**


| `gap_type`                       | `decision_type`            | Intent                               |

## 3. Current baseline (what already works)

**Orchestrator:** `run_manager_insights_fetch_debug` runs **1 → 0.5 → 2 → (optional §6 perception LLM + validate when `VECTOR_MANAGER_INSIGHTS_PERCEPTION_LLM`) → 3 (regex `extract_evidence`) → 4 (`link_work_items` with `CoordinationLinkInputBundle`: Step-3 evidence + validated `PerceptionRow` list) → 5 (`compute_gaps` with the same bundle + links; §6 Step 13) → 5.5 → 5.6 → 6 (`compute_signals` with the same bundle; §6 Step 14) → `compute_decisions` (§6 Steps 22–23 + 25–26) → `prioritize_decisions` (**§6 Steps 27 + 42**) → **§6 Step 28** cap → (optional **§6 Step 32** `**?persist_decisions=1`** upsert of capped rows) → 7 → 8**. Each response includes `**perception_qa`** (§6 Step 11). On this **admin** route only, **P7/P8 skip OpenAI** (`skip_llm=True`) and use deterministic fallbacks for speed unless `**?skip_interpretations=1`** / `**?skip_insights=1`** (§6 **Step 35**) — then the corresponding narrative bundle is **empty** and the generator is **not** invoked (stricter than fallbacks). Top-level `**decisions`** is the engine `DecisionBundle` (one row per gap); `**decisions_prioritized`** is the Steps **27–42** sort then truncated by **§6 Step 28** (`**?max_decisions=`** or env `**VECTOR_MANAGER_INSIGHTS_MAX_DECISIONS_SURFACED`**, default 3); debug fields on kept rows are preserved. With `**?persist_decisions=1`**, the same capped list is **upserted** into `**manager_insight_decisions`** and `**persisted_decision_ids`** echoes the deterministic UUID PKs in surface order.

**Admin API:** `GET /admin/tenants/{tenant_id}/manager-insight/fetch-debug?window_days=…` (optional `**persist_decisions=0|1`**, §6 Step 32; `**skip_interpretations=0|1`**, `**skip_insights=0|1**`, §6 Step 35); `**GET /admin/tenants/{tenant_id}/manager-insight/decisions**` — paginated list from `**manager_insight_decisions**` (§6 Step 33: `**limit**`, `**offset**`, filters; §6 Step 34 adds optional `**gap_id**`).**  
**Admin UI: `frontend/src/admin/AdminTenantManagerInsightPage.tsx` — fetch-debug (§6 Step 36: `**manager-insight-step36-fetch-debug-skip-controls`** + Step 35/36 notes) plus **Persisted decisions (database)** (§6 Steps 33–34): filters, paging, parity hint vs `**persisted_decision_ids`**, `**id` / `gap_id` / `run_id`** columns, copy-id.

**Execution graph (§6 Steps 15–17):** `build_execution_graph` + `ExecutionGraph` contracts are implemented and tested; fetch-debug `**execution_graph`** is **null** unless `**?include_execution_graph=1`** or `**VECTOR_MANAGER_INSIGHTS_INCLUDE_EXECUTION_GRAPH`** (§6 Step 16). **§6 Step 17** adds admin **Execution graph (4.5)** — tables for **nodes** / **edges** / **unresolved_dependency_refs** plus expandable raw JSON.

**Gaps + graph (§6 Step 18):** `**VECTOR_MANAGER_INSIGHTS_GAPS_USE_GRAPH`** (default off) merges execution-graph edges as undirected 1-hop adjacency inside `**compute_gaps`**; `**gaps.gaps_debug`** is a one-line QA string when the flag is on; admin P5 shows the line.

**Signals extension (§6 Steps 19–21):** `**SignalsV0Debug`** adds `**scope_ambiguity`**, `**discussion_churn`**, `**contradiction_density**` (same level enum as existing signals; default `**low**`). §6 Step 20 implements deterministic predicates + `**explain**` strings in `**compute_signals**`. §6 **Step 21** splits admin **P6 Signals** into **Core signals** vs **Coordination extension** (three rows + explain), with dedicated `**data-testid`** hooks.

**Implemented per [implementation plan status](manager_insights_implementation_plan.md#implementation-status-living):** Steps **0–8** of the **report** pipeline (contracts through insights), with tests under `backend/tests/vector/domains/manager_insights/` and contracts tests.

**Not done in that plan:** **Step 9+** (rendering, Slack report delivery, arbitration, orchestration, **persisted pipeline snapshots** as described there).

**Not done for coordination (this master plan):** **§6 Steps 43–46** (see §6 table for **Done**); **§6 Steps 37–42** (through **policy/outcome aggregates in prioritize**) are shipped. Remaining themes: Slack product, PM doc, optional admin nudge column (Step 43), etc.

**Prioritization (§6 Step 27 + §6 Step 42):** `**prioritize_decisions(bundle, signals=…, learning=…)`** returns a **sorted** `**list[DecisionBundleItem]`** (deterministic: decision type → urgent blocker nudge → combined gap key with learning demotion → id; formula in `**prioritize_decisions**` / `**decision_sort_learning**`).

**Cap (§6 Step 28):** After Steps 27–42, fetch-debug truncates `**decisions_prioritized`** to `**min(full_len, cap)`**; `**cap**` = `**?max_decisions=**` if present, else `**VECTOR_MANAGER_INSIGHTS_MAX_DECISIONS_SURFACED**` (default **3**, max **50**). `**perception_qa`** echoes query + applied cap + full count before cap.

**Decisions engine (§6 Steps 25–26):** `**compute_decisions`** may emit `**CLARIFY_SPEC`**, `**RECENTER**` / `**PAUSE_INVESTMENT**` (Step 25). `**HOLD_START**` (Step 26) when `**scope_ambiguity**` is high, no `**decision**`-kind evidence in the gap’s link/perception/graph neighborhood, and open issue/PR count in that neighborhood **>** `**VECTOR_MANAGER_INSIGHTS_HOLD_START_AFFECTED_WI_THRESHOLD`** (default **2**, i.e. at least three open execution items). `**decision_emission_debug`** on each row documents guard evaluation.

**Decisions admin (§6 Steps 24–29):** **P7 Decisions (coordination)** shows the engine table + **Prioritized surface** (§6 Step 29): `**rank`** 1..n, `**decision_type`**, `**gap_id**`, `**title**`, per-row **JSON** (same `DecisionBundleItem` shape as the engine table); collapsible header badges: engine row count + `**#surfaced/full · cap N`**; teal `**decisions_prioritized`** raw JSON remains in the teal block; **Coordination settings** / `**perception_qa`** unchanged from Step 28; `data-testid`s: `manager-insight-decisions-table`, `manager-insight-prioritized-decisions-table`, `manager-insight-p7-prioritized-surface-badge`.

**Persistence (§6 Steps 30–34):** PostgreSQL `**manager_insight_decisions`**. §6 Steps 30–32: table + ORM + fetch-debug upsert. §6 Step 33: list API + repo read path. §6 Step 34: optional `**gap_id`** filter; admin **full persisted view** (paging, DB parity columns, parity hint vs fetch-debug `**persisted_decision_ids`**).

### 6.1 Testing policy

1. **No §6 step merges without a defined verification** — use **§6.2** (add a row when splitting a step; never leave blank).
2. **Prefer automated:** `pytest` for Python; extend `**backend/tests/vector/domains/manager_insights/`** (or `contracts/`) with focused tests per **§6 step** where possible.
3. `**fetch-debug` shape changes:** include at least one test that calls `run_manager_insights_fetch_debug` (or the route handler) and **asserts presence/type** of new JSON keys (no need for full snapshot on every step).
4. **Admin-only steps:** require **manual script** in §6.2 *or* add a minimal **Playwright** / component test if the repo already uses it; otherwise QA sign-off in PR description is acceptable but must list exact clicks.
5. **HTTP new routes:** `pytest` with `TestClient` or async client — assert status + body schema.
6. **Migrations:** `alembic upgrade head` + `downgrade` in CI or documented manual run + ORM smoke insert/select test optional.
